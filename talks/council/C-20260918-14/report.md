## Phase 1 — 독립

### P1 (제안)

## 제안 1: 실행 설정 폴백을 명시적 선택으로 바꾸고 effective config를 산출물에 고정한다
- **바꾸는 것**: `eval_seal_tasks.sh`가 `model:` 블록이 있으면 공식 7-branch 설정으로 교체하는 동작을 (a) 삭제하거나, (b) 명시적 옵션이 없으면 실패로 만든다. 폴백을 안전장치로 유지하려면, 최소한 “요청 설정과 effective 설정이 다르다”는 사실을 로그와 산출물 메타데이터에 기록하고 성능 실행을 중단해야 한다. 실행 시작 시 요청 설정 경로·해시, 실제 적용된 설정 해시, branch list, 가중치, 코드 해시, 데이터·fold manifest 해시를 산출물에 기록한다. `ICF_*` 환경변수 복원은 이 제안에 포함하지 않는다.
- **바꾸는 전제**: “스크립트에 넘긴 설정 파일이 실제로 실행되는 설정이다”라는 전제를 뒤집는다. 현재는 `model:` 블록이 있으면 다른 설정으로 조용히 교체될 수 있다.
- **기대하는 차이**: 5-branch 요청과 7-branch 실행이 `max|Δprob|=0.000e+00`로 같은 확률 파일로 귀속되는 일이 새 실행에서 재현되지 않도록 한다. 정량 예측 불가. 기존 산출물은 이미 비트 단위로 동일하고 branch list·가중치·코드 해시가 기록돼 있지 않으므로 재귀속은 불가하다.
- **기전**: 확인된 폴백이 설정을 교체했으므로, 교체 경로를 차단하고 실제 설정을 기록하면 산출물과 구성이 1:1로 연결된다. 다만 다른 폴백·캐시·라이브러리 경로가 존재하는지는 미확인이다.
- **실패 조건**: 폴백이 이 스크립트 밖에서도 발생하거나, 과거 산출물에 기록이 없어 기존 기준선·게이트를 `verified`로 되살리지 못하면, 이 제안은 미래 실행만 보호한다.

## 제안 2: 성능 실행 전 config canary와 entrypoint echo를 필수 preflight로 둔다
- **바꾸는 것**: Primary 7 또는 SEAL 10 성능 실행 전에 다음을 넣는다. (1) 실제 entrypoint가 읽은 branch list와 가중치를 로그·메타데이터에 기록한다. (2) 요청 설정과 effective 설정이 다르면 실행을 중단한다. (3) 합성 canary에서 `sh`/`sj` 가중치를 1.0에서 0.0으로 바꾸면 margin이 변하는지 확인하는 회귀 테스트를 둔다. 확인된 `max|diff|=0.25`는 canary가 존재하는 증거로만 쓰고, 고정 임계값으로 쓰지 않는다.
- **바꾸는 전제**: “코드 여러 겹이 정상이고 출력이 같으면 원인 미확인”이라는 진단 방식을 “출력이 같다는 사실은 설정·경로·폴백이 동일했거나 비교 대상이 무효일 수 있다”로 바꾼다.
- **기대하는 차이**: 코드 내부를 다시 파기 전에, 실행 경로가 의도한 설정을 실제로 쓰고 있는지 판별해 오진 종료 시간을 단축한다. 정량 예측 불가.
- **기전**: YAML 파싱과 합성 데이터 margin 반응은 확인됐으므로, 남은 불확실성은 entrypoint가 그 설정을 실제 산출물 생성 경로까지 보존하는가이다. preflight가 확인될 때까지 실제 fold 산출물 경로 전체의 설정 보존은 미확인이다.
- **실패 조건**: canary가 실제 산출물 생성 경로와 다른 함수·스크립트를 검사하거나, 폴백이 preflight 이후·다른 계층에서 발생하면 막지 못한다. canary 통과를 성능 개선 근거로 오용하면 실패한다.

## 제안 3: 오염 검사를 값 앵커가 아니라 provenance 일치와 no-op 출력 비교로 재설계한다
- **바꾸는 것**: `PROJECT.md` §3.4의 fold-mean AUROC 4자리 일치(SMAD4 `0.4421`, PBRM1 `0.5553`)를 오염 검사 통과 기준으로 쓰지 않는다. 대신 `SCREEN_ONLY=1` 실행과 기저 실행의 요청/effective config hash, branch list, 가중치, 코드 해시, 데이터·fold manifest 해시, 그리고 원시 probability/margin을 비교한다. 5-branch 기저는 `configs/baseline/v121_active.yaml`을 요청 설정으로 쓰고, preflight가 effective config가 실제로 5-branch임을 확인한 뒤 비교한다. 기존 값 앵커는 회귀 참고값으로만 유지한다.
- **바꾸는 전제**: “값이 같으면 구성이 같다”는 전제를 뒤집는다. 현재 5-branch로 알고 있던 산출물과 7-branch로 지정해 실행한 산출물이 2459개 값에서 `max|Δprob|=0.000e+00`이므로, 값으로는 구성을 구분할 수 없다.
- **기대하는 차이**: 지금 수행 가능한 것은 기존 산출물의 오염 여부를 확인하는 것이 아니라, 새 실행 1쌍에 대해서만 오염 검사 통과를 주장하는 것이다. 비교 대상은 (a) provenance가 동일한지와 (b) 원시 출력이 동일한지다. 기존 산출물은 provenance가 없어 판별 불가이고, 과거 오염 통과 주장은 실행 무효로 둔다. 정량 예측 불가.
- **기전**: 폴백으로 구성이 교체된 것이 확인됐으므로, 값 일치는 구성 변화와 스크리닝 부작용을 구분하지 못한다. provenance와 원시 출력을 함께 비교하면 두 요인을 분리할 수 있다. 다만 `SCREEN_ONLY`가 실제 계산 그래프를 건드리는지는 아직 미확인이다.
- **실패 조건**: effective config가 아니라 requested config만 기록하면 폴백을 다시 놓친다. 학습 파라미터 도입 등으로 nondeterminism이 생기면 비트 단위 출력 비교가 오염이 아닌 변동으로 실패할 수 있다. 이 경우 판정 불가로 처리해야 한다.

- **더 단순한 설명**: 이번 오진의 원인은 "어떤 설정이 실제로 사용되었는지"를 알 수 없었기 때문이다. 폴백이 존재하는 한, 실행 시점의 유효 설정은 지정된 설정과 다를 수 있다. provenance 기록(실행 시점의 유효 설정 해시, 폴백 발동 여부, 코드 해시, 데이터 버전, fold manifest 해시)은 이 문제를 해결하는 유일한 수단이다.

**이론적 병목 1 — "설정 파일이 구성의 유일한 결정 인자" (제안 1·2·3 공통)**

- **이 가정이 깨지는 조건**: 설정 파일 밖에서 구성이 결정되는 경로가 존재할 때 — 코드 내 상수, 다른 환경변수, 라이브러리 기본값, 다른 폴백 계층.
- **깨질 때 나타나는 관측 가능한 증상**: effective config hash가 동일하게 기록됐는데도 산출물이 달라지거나, canary가 통과했는데 실제 fold 산출물이 요청 설정과 다름.

**이론적 병목 2 — "canary 경로 = 실제 산출물 경로" (제안 2)**

- **가정**: 합성 데이터 canary에서 sh/sj 가중치 변경이 margin을 바꾼다는 것이, 실제 fold 산출물 생성 경로에서도 설정이 보존된다는 것을 보장한다.
- **이 가정이 깨지는 조건**: canary와 실제 경로가 다른 entrypoint·함수·스크립트를 쓰거나, 폴백이 canary가 검사하지 않는 계층에서 발생.
- **깨질 때 나타나는 관측 가능한 증상**: canary 통과(합성 margin 변화)인데도 실제 fold 산출물이 5-branch 요청과 7-branch 요청에서 비트 단위로 동일.
- **문서의 어떤 관측이 이 가정과 충돌하는가**: 사실 2(합성에서 margin `max|diff|=0.25`)와 사실 3(실제 산출물 `max|Δprob|=0.000e+00`, 2459개 값)의 공존. 사실 4에서 폴백은 `eval_seal_tasks.sh` 레벨에서 발생. canary가 `eval_seal_tasks.sh`를 거치는지 문서에 없음 — 거치지 않으면 폴백을 검사하지 못한다.

**이론적 병목 3 — "provenance 완전성 = 구성 특정성" (제안 3)**

- **가정**: branch list·가중치·코드 해시·데이터·fold manifest 해시가 구성의 완전한 지문이며, 이 값들이 동일하면 구성이 동일하고, 다르면 구성이 다르다.
- **이 가정이 깨지는 조건**: provenance에 포함되지 않는 구성 결정 인자가 존재하거나, provenance가 requested를 기록하고 effective를 독립적으로 검증하지 못하면 폴백을 놓침.
- **깨질 때 나타나는 관측 가능한 증상**: provenance hash가 모두 동일인데 원시 출력이 다름, 또는 requested provenance가 다르면 effective가 같아 출력 동일.
- **문서의 어떤 관측이 이 가정과 충돌하는가**: 사실 3 — 5-branch 요청과 7-branch 지정이 비트 동일. requested 설정이 다르면 effective가 같아 출력 동일. 제안 3이 "requested/effective config hash"를 비교한다고 하지만, effective hash를 폴백 이후에 기록하는 것이므로, 폴백이 기록 경로보다 먼저 발생하면 requested만 기록될 수 있다. effective hash의 독립적 검증 경로 문서에 없음.

**이론적 병목 4 — "비트 단위 동일성 = 구성 동등성" (세 제안 공통, 특히 제안 3)**

- **가정**: 비트 단위 동일성은 두 구성이 실제로 같은 출력을 낸다는 증거로, 또는 두 구성이 동일하다는 증거로 해석된다.
- **이 가정이 깨지는 조건**: 비트 동일이 폴백으로 effective 설정이 같아진 결과일 때 — 5-branch와 7-branch가 실제로 같은 출력을 낸 것이 아니라, 둘 다 7-branch로 실행된 것.
- **깨질 때 나타나는 관측 가능한 증상**: 폴백 제거 후 5-branch 요청과 7-branch 요청의 출력이 달라짐(정상). 현재 비트 동일은 폴백의 증거이지 구성 동등성의 증거가 아님.
- **문서의 어떤 관측이 이 가정과 충돌하는가**: 사실 3과 4의 조합 — 비트 동일은 폴백(사실 4)으로 설명되며, 5-branch와 7-branch의 실제 출력 동등성을 입증하지 못한다. 제안 1은 "기존 산출물은 이미 비트 단위로 동일하고 branch list·가중치·코드 해시가 기록돼 있지 않으므로 재귀속은 불가"라고 인정하지만, 제안 3은 "provenance가 동일하면 구성이 동일"을 가정하여 이 구분을 충분히 하지 못한다.

- **더 단순한 설명**: 폴백은 공식 7-branch 구성(`D-042`)을 강제하는 안전장치일 수 있다. 확인된 사실(4)에 따르면 폴백의 트리거는 "설정 파일에 `model:` 블록이 있는가"다. 5-branch 설정 파일 `configs/baseline/v121_active.yaml`에 `model:` 블록이 있어 폴백이 발동했다면, `model:` 블록을 제거하는 것만으로 5-branch 실행이 가능하다. 폴백 자체를 삭제하면, 7-branch가 아닌 구성으로 실행될 수 있는 경로가 열린다. 이 경우 "결함"이 아니라 "5-branch 설정 파일의 `model:` 블록이 폴백 트리거에 걸리는 것"이 문제이며, 수정 대상은 폴백이 아니라 설정 파일이다. `v121_active.yaml`에 `model:` 블록이 존재하는지는 문서에 없음.
- **무엇이 참이면 이 주장이 무너지는가**: `v121_active.yaml`에 `model:` 블록이 없고, 그럼에도 폴백이 발동했다면, 폴백의 트리거가 `model:` 블록이 아니라 다른 조건이다. 이 경우 "model: 블록 제거"라는 단순 설명이 성립하지 않고, 폴백의 트리거 조건 자체가 불명확하므로 폴백을 삭제하거나 명시화하는 것이 정당한 수정이다.
- **이 반론의 한계**: 폴백이 안전장치인지 결함인지의 최종 판정은 사용자 결정 영역이다. R 좌석은 "더 단순한 수정 경로가 존재할 수 있다"는 것만 지적할 수 있다. 또한 `model:` 블록이 5-branch 설정의 필수 구조(예: 모델 아키텍처 정의)라면 제거가 불가능하고, 이 반론은 무효가 된다.

## 반론 2
- **공격 대상**: 제안 2의 "합성 canary에서 `sh`/`sj` 가중치를 1.0에서 0.0으로 바꾸면 margin이 변하는지 확인하는 회귀 테스트를 preflight로 둔다"
- **더 단순한 설명**: 이 canary는 이미 통과했다. 확인된 사실(2)에서 합성 데이터에서 `sh`/`sj`를 1.0→0.0으로 바꾸면 `max|diff|=0.25`로 margin이 변한다. preflight에서 이 테스트를 다시 실행하는 것은 이미 확인된 사실을 재확인하는 것이다. 실제로 미확인인 것은 "entrypoint가 요청 설정을 effective 설정으로 보존하는가"인데, 폴백은 entrypoint 레벨에서 설정 파일을 교체하므로, YAML 파싱과 margin 계산을 검사하는 canary는 폴백의 검사 대상이 아니다. canary가 통과해도 폴백이 작동할 수 있다.
- **무엇이 참이면 이 주장이 무너지는가**: canary가 entrypoint(폴백이 작동하는 계층)를 통과하도록 설계되어 있고, entrypoint에서 effective config를 echo하면, canary는 폴백을 감지할 수 있다. 제안 2는 "entrypoint echo"를 canary와 함께 preflight에 포함하므로, entrypoint echo가 폴백을 감지한다면 canary의 중복성은 entrypoint echo에 의해 상쇄된다.
- **이 반론의 한계**: "합성 canary"가 entrypoint를 포함하는지 문서에 없음. canary가 entrypoint를 포함한다면 이 반론은 무효다. 또한 제안 2의 실패 조건이 "canary가 실제 산출물 생성 경로와 다른 함수·스크립트를 검사하거나"라고 스스로 인정하므로, canary의 유효성은 미확인이며, 이 반론은 제안의 자기 한계를 반복하는 것이다.

## 반론 3
- **공격 대상**: 제안 3의 "provenance가 동일한지와 원시 출력이 동일한지를 비교한다"를 오염 판정의 필수 조건으로 두는 것
- **더 단순한 설명**: 오염 검사의 원래 목적(`PROJECT.md` §3.4)은 "SCREEN_ONLY 실행이 앙상블에 영향을 주지 않았는지" 확인하는 것이다. 폴백이 확인된 지금, SCREEN_ONLY=1 실행과 SCREEN_ONLY=0 실행이 같은 effective config를 가진다면(폴백이 같은 7-branch 설정으로 강제하므로), 원시 출력 비교만으로 오염을 판정할 수 있다. provenance 일치는 "어떤 산출물이 어떤 구성인지"를 귀속하는 데 필요하지만, "SCREEN_ONLY가 앙상블을 건드렸는지"를 판정하는 데는 effective config 일치 + 원시 출력 일치만 필요하다. provenance를 오염 판정의 필수 조건으로 넣으면, provenance 기록이 없는 모든 과거 실행이 "판별 불가"가 되는데, 이것은 `D-050`이 이미 선언한 상태의 반복이다. 제안 3이 "기존 산출물은 provenance가 없어 판별 불가이고, 과거 오염 통과 주장은 실행 무효로 둔다"고 한 것은 새로운 판정이 아니라 `D-050`의 재서술이다.
- **무엇이 참이면 이 주장이 무너지는가**: SCREEN_ONLY가 effective config를 변경할 수 있다면(예: SCREEN_ONLY=1일 때 폴백이 다른 설정으로 강제된다면), 원시 출력 비교만으로 오염과 구성 변화를 구분할 수 없다. 이 경우 provenance 일치가 오염 판정의 필수 조건이 된다. SCREEN_ONLY가 effective config에 영향을 주는지 문서에 없음.
- **이 반론의 한계**: `D-048` 이후 학습 파라미터가 허용되었고, `RU-97` §8에서 동일 구성에서 seed만 바꿔도 macro 폭 `0.0200`이 실측됐다. 비트 단위 원시 출력 비교는 학습 파라미터가 활성 경로에 있는 구성에서 성립하지 않을 수 있다. 이 경우 "원시 출력 일치" 자체가 무효가 되고, provenance 비교도 구성 귀속에는 필요하지만 오염 판정에는 충분하지 않다. 제안 3이 "판정 불가로 처리해야 한다"고 한 것은 이 한계를 인정하는 것이다.

## 반론 4
- **공격 대상**: 세 제안 전체의 "기대하는 차이" — "새 실행에서 재현되지 않도록 한다"
- **더 단순한 설명**: 세 제안 모두 "기존 산출물은 재귀속 불가"를 인정한다. 제안 1: "기존 산출물은 이미 비트 단위로 동일하고 branch list·가중치·코드 해시가 기록돼 있지 않으므로 재귀속은 불가하다." 제안 3: "기존 산출물은 provenance가 없어 판별 불가." 즉, 세 제안은 모두 미래 실행만 보호한다. `D-050`이 "계측 복구 전에는 게이트·승격 비교를 `verified`로 수행할 수 없다"고 한 판정은, 폴백이 확인된 지금도 그대로 성립한다. 폴백 확인은 "왜 5-branch와 7-branch 산출물이 비트 단위로 동일한지"를 설명하지만, "과거 산출물(0.6227, +0.56%p, 게이트 ①②)이 어떤 구성에서 나온 것인지를" 알려주지 않는다. 더 단순한 설명: "계측이 복구 불가"라는 `D-050`의 판정은 폴백 확인으로 바뀌지 않는다. 폴백 확인은 오진의 원인을 특정했지만, 과거 산출물의 구성 귀속을 가능하게 하지 않는다.
- **무엇이 참이면 이 주장이 무너지는가**: 과거 산출물에 기록된 메타데이터(예: 실행 로그에 effective config가 포함되어 있는 경우)가 존재하고, 이를 통해 구성을 귀속할 수 있다면, "재귀속 불가"가 성립하지 않는다. 하지만 확인된 사실(5)와 `D-050`에 따르면 "저장된 예측 파일에도 branch list·가중치·코드 해시가 기록돼 있지 않다." 실행 로그에 effective config가 기록되어 있는지 문서에 없음.
- **이 반론의 한계**: 실행 로그에 effective config가 포함되어 있다면, 과거 산출물의 일부는 구성 귀속이 가능할 수 있다. 이 경우 "재귀속 불가"가 전량에 성립하지는 않는다.

## 지지 (증거가 뒷받침함)
- YAML branch 가중치 파싱 경로가 동작한다: 7-branch 설정에서 `weight_sh=1.0`, `weight_sj=1.0`이 읽힌다는 실행 확인이 이를 뒷받침한다.
- `sh`/`sj` 가중치가 margin 계산에 반영될 수 있는 코드 경로가 존재한다: 합성 데이터에서 1.0→0.0 변경 시 `max|diff|=0.25`로 margin이 변한다는 확인이 이를 뒷받침한다. 범위는 합성 데이터와 확인된 경로로 한정된다.
- `eval_seal_tasks.sh`의 `model:` 블록 폴백이 5-branch 요청과 7-branch 지정 실행의 비트 동일성을 설명할 수 있다: 주어진 실행 확인에 따르면 폴백이 설정을 공식 7-branch로 교체하므로, 두 실행이 같은 effective config로 대체됐다면 `max|Δprob|=0.000e+00`(2459개 값)은 요청 설정 차이에서 나온 것이 아니다.
- `ICF_*` 환경변수 경로가 활성 branch control이 아니다: 비테스트 코드가 `ICF_*`를 읽지 않는다는 사실이 여전히 유효하다.
- 5-branch 설정 파일이 존재한다: `configs/baseline/v121_active.yaml`이 존재한다는 확인이 이를 뒷받침한다. 다만 이 파일이 실제 5-branch로 실행되는지는 별도 확인이 필요하다.
- 값 동일성만으로 구성을 구분할 수 없다: 서로 다른 구성으로 요청된 산출물이 2459개 값에서 비트 단위로 동일하다는 확인이, 값 앵커의 구성 식별 한계를 뒷받침한다.

## 반박 (증거가 반박함)
- “branch control 경로가 전혀 없다”는 주장은 반박된다: YAML 가중치 파싱과 합성 margin 반응이 확인됐으므로, 환경변수 경로가 없더라도 YAML 경로는 존재한다.
- “비트 동일성은 SH/SJ가 실제 WSI에서 기여 0이거나 코드 결함이다”라는 단일 해석은 반박된다: 합성 데이터에서 가중치 변경이 margin을 바꾸고, 폴백이 effective config를 교체할 수 있다는 확인이 있다. 따라서 동일성은 SH/SJ 무용의 증거가 아니다.
- “값 앵커(4자리 AUROC)로 오염 검사 통과를 판정할 수 있다”는 주장은 반박된다: 구성이 바뀌어도 값이 동일할 수 있고, 값 불일치도 구성 변화와 수치 드리프트를 구분하지 못한다.
- “폴백 확인만으로 과거 산출물을 verified로 귀속할 수 있다”는 주장은 반박된다: 저장된 예측 파일에 branch list·가중치·코드 해시가 없다는 `D-050` 기록은 폴백 확인으로 바뀌지 않는다.
- “provenance 기록 필요성이 줄었다”는 주장은 반박된다: requested config와 effective config가 다를 수 있는 경로가 확인됐으므로, 산출물 귀속과 오염 판정을 위해 provenance 필요성은 커진다.

## 판별 불가 (증거가 가르지 못함)
- `configs/baseline/v121_active.yaml`에 `model:` 블록이 있는지, 따라서 이 파일로 5-branch 실행이 가능한지는 문서에 없다.
- 폴백 트리거가 `model:` 블록뿐인지, 다른 조건에서도 폴백이 발생하는지는 문서에 없다.
- 합성 canary가 `eval_seal_tasks.sh` 또는 실제 fold 산출물 생성과 동일한 entrypoint 체인을 거치는지는 문서에 없다.
- `max|Δprob|=0.000e+00`의 2459개 값이 과제·fold·slide·class 중 어떤 축의 값인지, fold-level 350개 비교와 동일한지 문서에 없다.
- `SCREEN_ONLY=1`이 probability/margin 계산에 정상적으로 영향을 줄 수 있는지는 문서에 없다.
- 과거 저장 예측의 effective config, `0.6227`, `+0.56%p`, 게이트 ①·② 결과의 구성 귀속은 문서에 없다.
- 실제 WSI 데이터에서 `sh`/`sj` 가중치 1.0/0.0이 확률을 바꾸는지는 합성 확인만으로 확정되지 않는다.
- `BRANCHES_V121_5` 상수, `ICF_*` 외 환경변수, 라이브러리 기본값 등 설정 파일 밖 구성 결정 인자가 실행 경로에 존재하는지는 문서에 없다.
- 폴백이 결함인지 안전장치인지는 의도·승인·`model:` 블록 존재 여부가 확인되지 않아 판별 불가다. 어느 쪽이든 기록해야 할 항목은: 트리거 조건, requested config 경로/해시, effective config 해시, 폴백 발생 여부, 사용자 승인 또는 의도, `v121_active.yaml`의 `model:` 블록 존재 여부, 실행 중단 정책이다.
- 과거 오염 검사 통과 여부는 provenance 부재로 판별 불가다.
- fold manifest 해시가 fold ID 목록만인지 slide-level 분할 내용까지인지 문서에 없다.

## 실행 무효 (실행·계측 결함으로 판단 불가)
- 과거 값 앵커 기반 오염 검사(SMAD4 `0.4421`, PBRM1 `0.5553` 4자리 일치)는 구성 교체와 수치 드리프트를 구분하지 못하므로 통과 근거로 쓸 수 없다.
- 과거 `0.6227`, `+0.56%p`, 게이트 ①·② 결과를 `verified`로 인용하는 실행은 무효다. provenance가 없어 구성 귀속이 불가능하므로 `unverified-hold`로 유지해야 한다.
- requested config와 effective config가 다를 수 있는데 effective config가 기록되지 않은 실행은, 구성 특정 성능 주장에 대해 무효다.
- `configs/baseline/v121_active.yaml`이 `model:` 블록으로 폴백되면 7-branch가 되므로, 폴백 우회 또는 5-branch effective config 확인 전의 5-branch 기저 오염 검사는 무효다.
- `max|Δprob|=0.000e+00`을 “5-branch와 7-branch가 의도된 구성에서 같은 출력을 낸다”는 증거로 쓰는 것은 무효다. 이 동일성은 비교된 2459개 값에서 실제 실행 결과가 같았다는 사실만 보여준다.
