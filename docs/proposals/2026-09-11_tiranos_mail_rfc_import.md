# 제안서: TIRANOS Mail(Inbox)/RFC 협업 시스템의 ICF 도입 검토

- **작성자**: Owl / Idea Agent / claude-sonnet-5 (effort: medium) · 2026-09-11 00:00 KST
- **배경**: `/home/kimds/TIRANOS`에는 "Mail"이라는 이름의 시스템은 없었으며, 실제로는 두 축으로
  구성된 비동기 협업 프로토콜이 있었습니다.
  1. `talks/inbox/<role>/` — 역할별 Maildir 스타일 작업 큐 (`scripts/inbox.py`로 send/list/done 관리)
  2. `talks/rfc/RFC_TEMPLATE.md` — 문제정의(Navi)-대안가설(Kite)-구현사양(Pear)-최종판정(Navi)을
     **한 파일 안에서 각 역할이 직접 채워 넣고 동결**하는 단일 합의 문서
  - 이 문서는 "게시글-댓글 핑퐁 금지"를 명시적으로 금지 사항 1순위로 두고 있습니다.

  ICF의 현재 협업 방식(Agent 도구 동기 호출, `docs/proposals/`에 Owl 단독 작성,
  `docs/current_status.md`/`docs/history/archive.md`에 Orca가 판정을 별도로 기록)과
  비교했을 때, 무엇을 전제로 하고 있는지부터 의심하고 후보를 냅니다.

---

### 후보 1: 비동기 파일 큐(Inbox)로 세 에이전트 간 요청·응답 이력을 영속화

- **의심하는 전제**: 현재 ICF의 `Agent(agent="owl"/"lime", prompt="...")` 호출은 "세 에이전트가
  항상 같은 세션 타임라인 안에서 즉시 응답을 주고받는다"는 것을 전제합니다. 즉 Orca가 부재하거나
  다른 작업 중일 때 Owl/Lime에게 "나중에 처리할 요청"을 남겨 둘 영속적인 장소가 없습니다.
- **바꾸는 것**: `talks/inbox/{orca,owl,lime}/`와 유사한 디렉토리를 만들고, 세션 종료 시점에
  "다음 세션의 상대 역할이 확인해야 할 것"을 파일로 남깁니다. 세션 시작 시 자기 inbox를 먼저
  확인하는 절차를 핸드오프 규범에 추가합니다. `docs/agent_handoff.md`의 세션 시작 절차(§1)와
  결합하면, "Owl에게 지금 미완료로 남은 위임이 있는가"를 grep 한 줄로 파악 가능해집니다.
- **반증 조건**: Orca가 Owl/Lime을 호출하는 것이 항상 같은 대화 세션 내 동기 호출로만 이루어지고,
  세션 경계를 넘어 "지연된 위임"이 실제로 발생한 적이 없다면(즉 병렬·비동기 위임 수요 자체가
  없다면) 이 큐는 아무도 채우지 않는 빈 디렉토리로 남아 이식 실익이 없습니다. 또한 Agent 도구
  호출 자체가 이미 대화 로그로 완전히 영속화되고 있어 grep 가능한 형태로 조회할 수 있다면
  중복 인프라가 됩니다.
- **기전**: 파일 기반 큐는 세션이 끊겨도 사라지지 않고, "누가 누구에게 무엇을 요청했고 아직
  처리되지 않았는가"를 대화 로그를 뒤지지 않고 파일 목록만으로 확인 가능하게 합니다.
- **닫힌 축 저촉**: 없음 (협업 프로세스 변경이며 PSW·TGW·FC·P3-LIMIT-CURVE·LSAK와 무관).

### 후보 2: RFC 단일 동결 문서 — 제안·구현사양·판정을 한 파일에서 순차 완성

- **의심하는 전제**: 현재 ICF는 "제안은 Owl이 `docs/proposals/`에 원본으로 쓰고, 그에 대한
  Orca의 판정은 별도 문서(`docs/current_status.md` 또는 `docs/history/archive.md`)에 Orca가
  자기 언어로 다시 정리해 남긴다"는 것을 전제합니다. 두 문서가 물리적으로 분리되어 있습니다.
- **바꾸는 것**: 대규모 결정(예: `closed_axes.md`의 경계 재검토, 아키텍처 전면 개편급 후보)에
  한해, `docs/rfc/RFC_YYYY-MM-DD_<제목>.md` 같은 단일 파일을 만들어 "문제정의(Orca)-대안가설과
  반증조건(Owl)-구현사양·실측제약(Lime)-최종판정(Orca)" 네 섹션을 같은 파일 안에서 각 에이전트가
  직접 채우고, 판정 후 동결합니다. `AGENTS.md`가 이미 우려하는 "Main이 제안을 옮겨 적는 과정의
  취사선택" 문제를 판정 서술에도 동일하게 적용하는 것입니다.
- **반증 조건**: 만약 `docs/history/archive.md`의 결정 이력이 이미 항상 원본 제안서 경로를
  링크로 남기고, 판정 근거 서술이 요약이 아니라 원문 대조가 가능한 형태로 작성되고 있다면
  (즉 취사선택 손실이 이미 구조적으로 방지되어 있다면), 이 통합 문서는 불필요한 형식만
  추가하는 것이 됩니다. 또한 ICF 규범은 "정정은 본문을 덮어쓴다"(AGENTS.md §3)를 원칙으로 하는
  반면 RFC는 "영구 동결(Freeze)"을 원칙으로 하여, 재검토가 발생할 경우 두 원칙이 충돌합니다 —
  이 충돌이 실제로 재검토 빈도상 문제가 된다면 이 아이디어는 현재 형태로는 틀린 것입니다.
- **기전**: 미확인. 같은 파일 안에 나란히 있으면 대조가 "더 쉬워질 것"이라는 직관이지만,
  파일을 분리하고 상호 링크만 확실히 남기는 것과 실질적으로 얼마나 다른 효과를 내는지는
  측정된 바 없습니다.
- **닫힌 축 저촉**: 없음. 단, `closed_axes.md`의 "경계 재검토" 절차 자체를 RFC 형식으로 옮길
  경우 문서 구조가 바뀌므로 Document 역할과의 조율이 필요합니다(채택 여부는 Orca 판단).

### 후보 3: "빈 inbox = 0토큰 즉시 종료" 원칙의 세션 시작 절차화

- **의심하는 전제**: 현재 ICF는 Owl/Lime이 항상 Orca의 `Agent()` 호출(pull)로만 소환되고,
  스스로 "나에게 온 미해결 요청이 있는가"를 먼저 확인하는 자기주도적 진입점이 없다는 것을
  전제합니다. TIRANOS는 이를 "세션 시작 시 수신함이 비어 있으면 0토큰으로 즉시 세션 종료"로
  명문화하고 있습니다.
- **바꾸는 것**: 후보 1의 inbox 디렉토리가 도입된다면, 각 역할 세션 시작 시 자기 inbox를
  가장 먼저(다른 문서를 읽기 전에) 확인하는 절차를 `AGENTS.md`/`docs/agent_handoff.md`에
  추가하여, 위임이 없으면 최소 토큰으로 대기 상태를 유지하게 합니다.
- **반증 조건**: Owl/Lime 세션이 애초에 Orca의 프롬프트 없이는 생성되지 않는 순수 push 구조라면
  (지금 실제로 그러합니다), "세션 시작 시 수신함을 스스로 확인한다"는 절차는 적용될 대상이
  없습니다 — 세션 생성 자체가 이미 위임 프롬프트를 담고 있기 때문입니다. 이 경우 이 후보는
  후보 1이 채택되어 "Orca 프롬프트 없이도 Owl/Lime이 주기적으로 깨어나 자기 inbox를 확인하는"
  실행 체계가 별도로 만들어질 때만 의미를 가집니다.
- **기전**: 미확인.
- **닫힌 축 저촉**: 없음.

### 후보 4: 역할별 inbox를 "정보 격리"의 물리적 채널로 사용

- **의심하는 전제**: `research_hierarchy.md` 규칙 5("접근은 자료의 용도에 따라 나눈다",
  "독립 검증을 위해 보류한 자료는 정해진 시점까지 누구도 열람하지 않는다")가 현재는 저장소
  전체를 모든 역할이 동일하게 열람 가능한 상태에서 **규범적 권고**로만 존재한다는 것을
  전제합니다. 물리적으로 "이 자료는 Owl에게 전달되지 않았다"를 파일 시스템 수준에서 표현할
  방법이 없습니다.
- **바꾸는 것**: 역할별 inbox 디렉토리를 "전달된 자료의 기록"으로 사용하여, Orca가 특정 자료를
  의도적으로 Owl에게 전달하지 않은 시점(예: 독립 검증용 보류 데이터)을 "그 자료가 Owl의 inbox
  경로에 없다"는 사실로 감사(audit) 가능하게 만듭니다. 이는 정보 제한을 "안 보여줬다고 말로
  약속하는 것"에서 "안 보여준 경로가 파일로 남는 것"으로 바꿉니다.
- **반증 조건**: 세 에이전트가 이미 같은 파일시스템 전체에 대한 Read 권한을 신뢰 기반으로
  공유하는 구조이고 이 권한이 기술적으로 제한 불가능하다면(우회 가능), inbox 디렉토리를
  만들어도 실질적 접근 제한 효과는 없고 감사 흔적만 추가하는 것에 그칩니다. 이 경우 "정보
  제한"이라는 목적은 달성되지 않고 "정보 제한을 시도했다는 기록"만 남습니다 — 이것이 원래
  목적(발상 단계에서 기존 점수의 영향을 줄이는 것)에 기여하는지는 판별 불가입니다.
- **기전**: 기전 미확인. 파일 시스템 권한(chmod, 별도 워크트리 등)으로 실제 강제가 가능한지는
  Coding(Lime)의 실측 영역입니다.
- **닫힌 축 저촉**: 없음.

## 공통 메모

- 네 후보 모두 연구의 실체(PSW·TGW·FC·P3-LIMIT-CURVE·LSAK)를 건드리지 않고, **에이전트 간
  협업 프로세스**만 바꿉니다. 따라서 채택 여부와 무관하게 `docs/closed_axes.md`의 경계와는
  저촉되지 않습니다.
- 네 후보는 서로 배타적이지 않습니다. 예컨대 후보 1(inbox)이 먼저 도입되어야 후보 3(0토큰
  확인 절차)과 후보 4(정보 격리 채널)가 의미를 가집니다. 후보 2(RFC)는 독립적으로 도입
  가능합니다.
- TIRANOS의 "게시글-댓글 핑퐁 금지" 원칙 자체는 ICF에도 이미 유사하게 적용되고 있습니다
  (`docs/current_status.md` 100줄 제한, "정정은 본문을 덮어쓴다" 원칙). 이 부분은 새로
  이식할 필요가 없어 후보에서 제외했습니다.
- 실제 도입 여부, 우선순위, `scripts/inbox.py` 이식의 구현 비용 실측은 Orca의 판정과
  Lime의 실측 영역입니다.
