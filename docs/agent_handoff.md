# ICF 에이전트 핸드오프 — 역할별 실행 가이드

역할·책임·결정 권한·공통 연구 행동 원칙은 [AGENTS.md](../AGENTS.md)에 정의합니다.
이 문서는 해당 역할로 **무엇부터 확인하고, 어떤 작업을 수행하며, 무엇을 남겨야 하는지** 안내합니다.
외부 연구 규범을 읽어야 수행할 수 있는 지시는 두지 않습니다. 아래 프로젝트 문서 링크는
현재 목표·사양·근거를 찾기 위한 경로이며, 에이전트 정의를 외부 문서에 위임하지 않습니다.

## 0. 세션 진입과 역할별 작업 경로

### 0.1 공통 시작

1. 사용자 지시에서 맡은 역할·목표·범위·기존 승인과 예산을 확인합니다. 단순 보조 작업에
   여러 전문 역할을 가정하지 않습니다. 전문 역할이 필요한 경우 AGENTS.md의 협업 경로를 사용합니다.
2. 저장소 루트에서 `git status --short`와 관련 diff를 확인합니다. 재개·동기화 요청이면
   `git fetch origin`으로 원격 변경을 확인하고, 미커밋 작업을 보존하며 안전하게 동기화합니다.
3. [PROJECT.md](PROJECT.md)에서 목표·완료 조건을, [current_status.md](current_status.md)에서
   진행 RU·블로커·다음 행동을 확인합니다. 다음 명령도 현재 지시와 유효한 사양에 맞는지 검토합니다.
4. 아래 역할별 입력만 추가로 읽습니다. 문서 전체 점검은 Document의 주요 변경·단계 종료 작업에서
   수행합니다. 제한된 자료는 내용을 열지 말고 허용된 메타데이터만 확인합니다.
5. 실행이 필요하면 `hostname`, `command -v sinfo`, `command -v nvidia-smi`와 사용 가능한
   GPU·드라이버를 실측하고 §5에 따라 환경을 설정합니다. 과거 호스트 기록을 현재 값으로 믿지 않습니다.
6. 재개 브리핑은 현재 목표 / CLEAN 또는 WIP / 블로커 / 바로 할 다음 행동을 5줄 내외로 적습니다.
   문서 편집·환경 점검 등은 연구 실험이 아니므로 RU 없이 진행한다고 짧게 밝힙니다.

### 0.2 역할별 입력 → 작업 → 완료 산출물

#### Platform으로 시작한 경우

- **입력**: 사용자 요청, `current_status.md`, 관련 RU 카드와 담당 역할의 실행·후속 작업 명세.
- **작업**: 요청을 분류하고 필요한 역할에 §0.3 형식으로 전달합니다. 실행 전 §1의 범위·예산·
  접근 제한과 §5 환경을 확인하고 §6 명령을 실행합니다. 명령·환경·종료 코드·로그·산출물 위치를
  기록하여 Coding에 돌려줍니다. 판정이 필요한 근거는 Reasoning에, 문서 변경은 Document에 전달합니다.
- **완료**: 실행 결과와 해석을 구분한 짧은 보고, 남은 의존성·다음 담당자, 갱신된 현재 상태.
  승인 계획 안의 다음 작업은 계속하고 방향·판정 기준 변경만 해당 권한자에게 연결합니다.

#### Reasoning(Orca)으로 시작한 경우

- **입력**: `PROJECT.md`의 목표·판정 설계, [research_directions.md](research_directions.md)의 후보 큐,
  [closed_axes.md](closed_axes.md)의 경계, 해당 제안·RU·Coding 검증·실행 기록.
- **작업**: 질문과 줄일 불확실성을 정합니다. 방향이 미정이면 탐색을 설계합니다. 후보 심사 때
  닫힌 축의 실제 기전·경계를 대조하고 모호한 항목은 `closed_axes.md` §3에 남깁니다.
  §1의 카드에 비교 조건·자료 접근·예산·기준·중단 조건을 구체화하고 전문 작업을 연결합니다.
  결과를 받으면 §4 보고 계약과 계획 이탈을 확인하고 증거 판정과 운영 결정을 각각 적습니다.
- **완료**: 근거·한계·재검토 조건이 있는 결정, 다음 작업의 목표·제약·예산, Document에 넘길
  변경 목록. 기준·방향·구성 변경은 `history/archive.md` 결정 이력에 남기며 미위임 변경은 사용자에게 요청합니다.

#### Idea(Owl)로 시작한 경우

- **입력**: 현재 목표, `research_directions.md`, 관련 구조를 다룰 때
  [current_architecture.md](current_architecture.md), 허용된 탐색·개발 결과.
- **작업**: 해결할 한계와 기존 전제를 드러내고 대안별 바꾸는 전제·기대 관측·반증 조건·미확인
  사항을 적습니다. `closed_axes.md`와의 관계는 제약과 대안으로 보고하며 스스로 최종 기각하지 않습니다.
  아직 확인하기 어려운 접근도 제시하고 작은 프로브가 배울 내용을 설명합니다.
- **완료**: `docs/proposals/`에 제안서를 작성합니다(경로가 없으면 생성). 후보 큐에 제안 위치와
  미심사 상태를 연결하고 우선순위 확정·예산·심사는 Reasoning에 요청합니다. 큐 등록만으로 실행하지 않습니다.

#### Coding(Lime)으로 시작한 경우

- **입력**: 승인 사양과 RU, `current_architecture.md`, 대상 코드, `scripts/lib/arms.sh`, 관련 테스트.
- **작업**: §3 불변식을 확인하고 구현·검증 코드와 예상 동작을 준비합니다. 변경 사양·환경·명령·
  비용 추정·중단 조건을 실행자에게 제공합니다. Platform 없는 직접 작업은 §5~§6에 따라 실행합니다.
  로그·예측 파일로 의도한 개입과 실제 동작을 대조하고 필요한 회귀 검사를 수행합니다.
- **완료**: 변경 파일, 재현 명령, 수행/미수행 검증, 실측과 추정을 구분한 비용·한계 보고.
  사양 안의 오류는 고쳐 기록하고, 사양 문제는 Reasoning에 근거와 함께 전달합니다.
  구현·수식·실행 방식 변경은 Document가 동기화할 위치와 근거를 함께 넘깁니다.

#### Document로 시작한 경우

- **입력**: 변경 요청과 diff, [README.md](README.md)의 문서 지도, 관련 결정·RU·검증 보고·실행 기록.
  최신 문서의 날짜만으로 정본을 선택하지 말고 아래 표의 담당 문서와 실제 근거를 대조합니다.
- **작업 순서**:
  1. 변경 사실·출처·확인 상태를 추려 아래 표로 영향 문서를 찾습니다. 없는 결과는 채우지 않고
     미확인으로 남깁니다. 제한 자료는 위치·상태 등 허용 정보만 관리합니다.
  2. 해당 정본의 현행 설명을 수정한 뒤 참조 문서의 표현·링크·상태를 함께 맞춥니다.
     수치·기준을 여러 문서에 재선언하지 않습니다. 기존 기록이 충분하면 새 보고 양식을 만들지 않습니다.
  3. 단순 표기·링크·명백한 사실 불일치는 근거로 수정합니다. 구현 충돌은 Coding과 실행 기록으로
     확인하고, 연구 결론·사양·기준 충돌은 양쪽 출처와 쟁점을 남겨 Reasoning에 전달합니다.
     답변 전에는 미해결로 표시하고 충돌과 무관한 갱신은 계속합니다.
  4. 주요 변경 이후나 단계 종료에는 `rg --files docs`와 문서 지도로 전체 목록을 대조하여
     목적·상태·정본·유입 링크를 점검합니다. 고립된 문서는 지도나 관련 진입점에 연결하고,
     중복은 정본 링크로 줄입니다. 오래된 문서는 상태와 대체 경로를 표시하여 이력과 유일 정보를
     보존하며 보관하고, 이동 시 참조도 갱신합니다.
  5. §7의 자기완결성·이력 보존·상태 줄 수를 확인하고 §5 환경에 맞게
     `bash scripts/run_tests.sh test_docs_consistency.py`를 실행합니다 (문서 단독 변경 시 전체 회귀 스위트 discover 실행 금지).
- **완료**: 변경 문서와 근거, 점검 범위·검증 결과, 미해결 충돌과 담당자, 다음 갱신 조건을 보고합니다.
  문서가 일치한다는 사실과 연구 주장이 검증됐다는 판단을 구분합니다.

| 변경된 내용 | 갱신할 정본과 후속 확인 |
|---|---|
| 역할·권한·공통 연구 행동 | `../AGENTS.md`; 이 문서의 역할별 실행 경로가 맞는지 확인 |
| 역할별 절차·RU 운영·환경 규칙·문서 유지 | `agent_handoff.md`; `README.md`의 지도·참조 확인 |
| 목표·기준선·승격 기준·게이트·판정 설계 | `PROJECT.md`; 승인된 결정 출처 확인 후 큐·현재 상태의 참조 갱신 |
| 현재 작업·블로커·다음 명령·환경 실측 | `current_status.md`; 100줄 이내 유지 |
| 후보와 우선순위·제안 | `research_directions.md` §0, 해당 제안서; 제안·승인·착수 상태 구분 |
| 구조·브랜치·수식·집계 구현 | `current_architecture.md`; Coding 보고와 코드·검증 근거 대조 |
| 닫힌 축·경계·재개 조건 | `closed_axes.md`; 미확정 경계와 판정 완료 항목 구분 |
| 실행·연구 결과 | 열린 `ru/` 카드, 종료 시 `history/research_units_all.md`와 `.json`, 관련 `reports/` |
| 규범·기준·구성 결정 또는 정정·철회 | `history/archive.md`; 원래 기록을 보존하고 변경 근거 추가 |
| 문서 생성·이동·보관 | `README.md` 지도와 해당 참조; 목적·상태·정본/대체 경로 명시 |

### 0.3 호출·전달·서명

기존 호출 래퍼는 저장소 루트에서 사용합니다. 사용자에게 특정 에이전트 호출을 지시받으면
해당 세션을 실제 호출하고, 그 결과와 현재 세션의 추가 설명을 구분해 전달합니다.

```bash
bash scripts/call_agent.sh orca "<연구 설계·판정 요청>"
bash scripts/call_agent.sh owl "<새 접근·반증 조건 요청>"
bash scripts/call_agent.sh lime "<구현·기술 검증 요청>"
```

래퍼의 기존 `main` 별칭은 `orca`를 호출합니다. 호출 문자열이 운영·판정 권한을 추가하지 않습니다.
Platform·Document 전용 래퍼 대상은 현재 없으므로 사용자가 해당 역할로 직접 지정한 세션이나
허용된 별도 에이전트 도구를 사용합니다. 역할 이름만 바꾸어 별도 세션을 호출한 것처럼 보고하지 않습니다.
기존 호출 설정에 오래된 역할 설명이 있더라도 작업 전달에 이 두 문서의 현행 역할·권한을 명시합니다.

- **요청**: 목표 / 관련 근거 위치와 변경 / 범위·제약·자료 접근·예산 / 기대 산출물·완료 조건.
- **반환**: 산출물·변경 파일 / 근거 위치 / 실행 사실·기술 확인·연구 판정과 각 주체 /
  실패·불확실성·미수행 / 후속 작업·필요 담당자. 전체 원문을 반복 전달하지 않습니다.
- **서명 형식**: `[작성자: <실제 이름> / <역할> / <실제 모델> (effort: <실제 값 또는 미확인>) · YYYY-MM-DD HH:MM KST]`.
  문서·보고서는 본문 말미, 커밋은 본문에 남깁니다. 코드 등 형식 제약이 있는 작업물은 연결된
  변경 보고나 커밋에 기록합니다. 기존 작성자·판정 출처는 보존하고 새 편집자의 서명을 구분합니다.

## 1. 진행 프로세스 — 연구 단위(RU) 카드

### 1.0 착수 판단과 자원

성능·기전·구조 주장이나 채택·방향 판단의 근거를 만들거나, 모델·데이터·평가 설정을 바꾸어
새 수치를 만들거나, 기존 수치를 바꾸는 계측 결함을 수정하는 작업은 RU로 관리합니다.
문서 편집, 기존 결과의 재출력, 환경 점검, 회귀 검사, 결과 해석에 영향 없는 정리는 카드 없이 수행합니다.
분류가 애매하면 결과가 어떤 주장·결정에 쓰이는지 밝히고 필요한 기록 수준을 정합니다.

1. 현재 목표와 줄일 불확실성을 적습니다. 착수 후보는 `research_directions.md` §0 큐에 연결합니다.
   큐 등록은 예산 승인이나 채택이 아닙니다. 방향이 미정이면 방향 탐색임을 명시합니다.
2. `closed_axes.md`와 대조합니다. 저촉 가능성이 있으면 축 ID·기각 기전·실제 저촉 근거·경계 밖
   대안을 보고합니다. 판정이 갈리면 §3 미확정 목록에 올리고 해당 후보 실행은 보류합니다.
   기존 경계 안의 실행은 하지 않으며, 재개·전환 결정은 위임 범위 안의 Reasoning 또는 사용자에게 연결합니다.
3. §1.1 카드에 필요한 내용을 채웁니다. 일부 필드가 없으면 기존 지시·사양 안에서 초안을 완성합니다.
   이미 승인된 범위는 재확인 없이 진행합니다. “돌려봐”라는 요청에도 확인 목적·범위·비용·중단
   조건을 구체화하며, 미위임 목표·기준·예산 결정만 근거와 권고를 준비해 사용자에게 요청합니다.
4. 신규 브랜치는 `PROJECT.md` §5의 게이트 ① 직교성 → ② 정보량 순서로 진행합니다.
   게이트 ① 탈락 시 성능을 조회하지 않고 해당 실행을 종료합니다. 접근 전체에 대한 판정과 구분합니다.
   자료의 사용 목적·접근 허용 시점은 카드에 기록하고 SEAL 보류 상태는 `PROJECT.md` §3.1에서 확인합니다.
5. §5 호스트 규칙과 할당 자원·기존 승인·예산을 확인합니다. 중단 조건이나 예산에 도달하면
   실행을 멈추고 결과와 이유를 전달합니다. 추가 자원이 승인되었다고 추정하지 않습니다.

### 1.1 착수 전 카드 작성

```bash
source scripts/node_env.sh
$PYTHON scripts/docs/ru.py open --title "<하나의 연구 질문>"
# 생성된 docs/ru/RU-xx.json을 작성한 뒤
$PYTHON scripts/docs/ru.py validate --id RU-xx
```

`type`은 `exploratory` / `diagnostic` / `confirmatory` / `reproduction_measurement` 중 고릅니다.
유형 전환 시점과 이미 본 자료를 기록합니다. 탐색에는 완성된 기전 가설을 요구하지 않습니다.
도구의 필수 필드 검사가 연구 설계의 타당성까지 검증하는 것은 아닙니다.

| 필드 | 작성할 내용 |
|---|---|
| `question` | 답하려는 질문, 줄일 불확실성, 어떤 지식·판단에 쓰는지 |
| `hypothesis` | 확증의 주장 범위, 진단의 경쟁 설명. 탐색은 `미정` 허용 |
| `criteria` | 확증은 결과 전 판정 규칙, 탐색은 완료·선택 기준. 판별 불가·실행 무효 처리 |
| `budget` | 승인된 시간·계산 비용 상한 |
| `kill` | 즉시 또는 상한 도달 시 중단할 조건 |
| `next_actions` | 결과별 채택·추가 진단·보류·종료 등 후속 행동과 담당자 |

해당 없는 필드는 `해당 없음: 이유`로 적습니다. 비교군·표집 단위·고정 조건은 `design`,
코드·설정·데이터 버전과 이미 본 평가 자료는 `provenance`, 닫힌 축 대조는 `closed_axes_check`에
기록합니다. 확증은 결과를 보기 전에 주장·기준·비교·자료 접근 계획을 정합니다.

### 1.2 관찰·분석·판정의 적용 규칙

- **R1 — 탐색**: 무엇을 발견하려는지와 후보 범위의 이유를 적고, 필수 제약과 구현 관습을
  구분합니다. 불확실한 접근도 승인 예산 안에서 작은 프로브로 시험하고 배운 것을 남깁니다.
  연구 방향 없이 점수만 최적화하는 일과 탐색을 확증으로 포장하는 일을 각각 점검합니다.
- **R2 — 이상값**: 계측·구현의 값싼 오류부터 예산 안에서 확인합니다. 상수 출력·손실은 기대
  동작과 표시 정밀도를 대조합니다. 모든 도구의 완전한 증명을 가설 검토의 선행 조건으로 삼지 않습니다.
- **R3 — 기전**: 분기 활성·상관·랭크·분산은 단서입니다. 경험적 우위만 확인했으면
  `기전 미확인`을 적습니다. 실패 시 의도한 개입·계측·검정력을 확인하여 반박 범위를 한정합니다.
- **R4 — 선택 이력**: 사후 변경은 원래 계획과 그 기준의 결과를 보존하고 이유를 남깁니다.
  새 분석은 탐색으로 표시합니다. 선택에 사용한 자료를 독립 최종 검증으로 취급하지 않습니다.
- **R5 — 불확실성**: `PROJECT.md` §4의 추정 대상과 표집 단위를 확인하여 fold별 대응 차이를
  계산합니다. 과제 내 fold 의존성을 고려하고 동일한 시드 반복을 독립 표본으로 세지 않습니다.
  개선량과 과제 군집 CI·SE·과제별 악화를 별도로 보고합니다. 개선량 기준을 CI 하한 기준이나
  상대 증가율로 바꾸지 않습니다. SD·SE·CI·MDE·채택할 가치가 있는 최소 개선량을 구분하고
  MDE를 성공 컷오프로 쓰지 않습니다. 고정 과제의 관측을 과제 모집단 전체로 일반화하지 않습니다.
- **R6 — 조합과 기여**: 현행 조합은 유효한 평가로 검증합니다. 승격 시점의 차이나 조합의
  성공만으로 개별 브랜치의 효과를 확정하지 않으며, 효과 주장은 §4의 통제 비교로 뒷받침합니다.
- **R7 — 판정 기록**: 증거는 `지지 / 반박 / 판별 불가 / 실행 무효`(탐색은 `탐색 완료`),
  운영은 `채택 / 추가 진단 / 보류 / 종료`로 나누어 적습니다. 예산 종료가 반박을 뜻하지 않고,
  효과 지지가 채택을 강제하지 않습니다. 실행자는 사실을, Coding은 기술 확인을 제공하며
  연구 판정은 Reasoning이 맡습니다.

### 1.3 종료와 정정

실행자가 명령·환경·로그·실제 변경을, Coding이 기술 검증을, Reasoning이 연구 판정과 다음
목표·제약을 남깁니다. Document 또는 직접 작업 담당자는 그 근거로 카드를 정리합니다.
`experiment`·`observations`·`decision`을 채우고 기전의 확인 범위/잠정 설명/미확인,
계획 이탈·실패·악화·누락 실행·미해결 사항을 함께 남깁니다.

```bash
$PYTHON scripts/docs/ru.py close --id RU-xx
```

종료 결과는 `history/research_units_all.md`와 `.json`에 append됩니다. RU 종료만으로 별도
결정 레코드를 만들지 않습니다. 규범·기준·구성이 바뀌면 `history/archive.md`에 결정 근거를
추가하고, 축을 닫거나 열면 `closed_axes.md`에 기각 기전·경계 안·경계 밖·재개 조건을 반영합니다.
관련 커밋 본문에 RU ID를 적습니다. 현행 설명은 바로잡되 원시 증거·사전 계획·과거 판정은
보존하고 정정 이력을 연결합니다. 문서 정합성 검사는 §7.1을 사용합니다.

## 2. 프로젝트 개요

**ICF**는 미리 추출된 MIL 패치 임베딩(UNI2, 1536D) 위에서 병리 WSI를 분류하는 **in-context
분류기**다. 활성 구성은 **학습 파라미터 0개의 완전 결정론적 통계 앙상블**이다 —
Context 슬라이드만으로 within-slide PCA 기저(K=256)를 만들고, 상보적 통계 브랜치들이 각각
독립 마진을 산출한 뒤 Trimmed Mean으로 결합한다.

- 목표·기준선·승격 기준: [`PROJECT.md`](PROJECT.md)
- 브랜치 정의와 수식: [`current_architecture.md`](current_architecture.md)

## 3. 핵심 불변식 (Core Invariants)

회귀 스위트가 검사한다. 위반하는 변경은 병합하지 않는다.

1. **무유출 계약 (Zero Data Leakage)**
   Query 슬라이드는 within-slide PCA 기저 구축, 토큰 사전 생성, 정규화 통계에 **일절
   참여하지 않는다.**
2. **정확한 라벨 반대칭 (Exact Label Antisymmetry)**
   라벨 반전($y \to 1-y$) 시 브랜치 마진의 부호가 정확히 반전되고 확률이 여집합이 된다
   ($P(1-y) = 1 - P(y)$).
3. **결정론적 평가 (Deterministic Evaluation)**
   seed std는 `0.00000`이어야 한다. **같은 실행을 반복해 얻은 동일 점수는 새로운 독립 증거가
   아니므로 시드 반복을 표본 수로 세지 않는다.** 이는 표본 단위에 대한 제약이지 통계 도구의
   금지가 아니다 — **fold는 데이터 표집 단위이므로 구간 추정을 쓴다**
   (결정 이력 `D-018`·`D-019`. `D-003`은 폐지됐다).
   비교 기준·승격 기준·판정 설계의 **수치는 [`PROJECT.md` §3~§4](PROJECT.md)가 정본**이다.
4. **닫힌 축 준수**
   `D-022`의 PSW·TGW / FC / P3-LIMIT-CURVE / LSAK는 비저촉으로 확정했다.
   해당 연구를 과거 경계 논쟁만으로 중단하지 않는다.
   [`closed_axes.md`](closed_axes.md)의 `경계 안`에 해당하는 제안은 성능·점수와 무관하게
   실행하지 않고 기존 판정과 저촉 근거를 보고한다. 경계 판단이 갈리면 **임의로 한쪽을 채택하지 않고** 같은 문서 §3의 미확정
   목록으로 올린다.

## 4. 보고 무결성 계약 (Reporting Integrity Contract)

§214에서 실제 위반이 확인되어 신설됐다 (결정 이력 `D-006`·`D-010`·`D-011`).

- **회귀 전량 명시 의무**: 성능이 하락한 과제를 생략할 수 없다. 상승 과제만 나열한 요약은 금지한다.
- **Sign agreement 병기 의무**: macro AUROC를 제시할 때 `n/7`을 같은 줄에 병기한다.
- **측정 방식 정확 기술**: 저장된 마진의 **오프라인 재집계**를 "전수 실측"으로 표기하지 않는다.
  신규 파이프라인 실행(`logs/`·`predictions/`에 신규 산출물 발생)과 재집계를 용어로 구분한다.
- **비교 모집단 한정**: "1위", "최고", "경신"에는 비교 대상 집합을 괄호로 한정한다.
- **승리 수식어 금지**: "폭등", "사상 최고", 이모지 강조 등을 쓰지 않는다. 수치와 부호로만 기술한다.
- **미검증 항목 표기 의무**: 수행하지 않은 검증(SEAL hold-out 등)은 침묵하지 않고 `미검증`으로 명시한다.
- **자기 검증 우선**: 문서화 전에 저장된 예측 파일로부터 독립 재계산해 대조한다.
- **Oracle 금지**: 브랜치 간 최댓값("과제별 최상 단독 브랜치")을 판정 기준·상한·미회수 성능으로
  쓰지 않는다. 참고 수치로 표시할 수는 있으나 **어떤 채택·승격·연구 방향 판정의 근거로도 쓰지 않는다.**
- **통제 비교 의무**: 어떤 기법의 **효과**를 주장하려면 **동일 실행·동일 basis·동일 fold에서
  그 기법만 토글한** 비교여야 한다. 서로 다른 실행의 표를 나란히 놓고 차이를 효과로 해석하지 않는다.

## 5. 실행 환경

현재 접속 호스트의 실측값은 `current_status.md`를 따른다.

> **실행 방식은 호스트에 종속된다** (`D-030`). 세션 시작 시 `hostname`·GPU·`sinfo` 유무를
> **실측해** 아래 둘 중 어디에 해당하는지 정하고, 문서에 적힌 과거 호스트를 그대로 신뢰하지 않는다.
>
> | 호스트 유형 | 실행 방식 |
> |:---|:---|
> | **`nexgem`** — GPU 없음, Slurm 제출 가능 | 계산은 전부 `sbatch`로 제출한다. 아래 Slurm 규칙 전체가 적용되며 사용자가 승인한 제출 범위·예산을 확인하고, 미승인 제출이면 승인을 받는다. |
> | **`nexgem-s1`** — GPU 8장, `sinfo`·`squeue` 없음 | Slurm을 쓰지 않고 **직접 실행**한다. `sbatch` 의무·노드 등급 우선순위·job 로그 규약은 **적용되지 않는다**. GPU 예산은 RU 카드에 적는다. |
>
> 다른 호스트를 로그인 노드나 특정 Slurm 노드와 동일시하지 않는다. 새 호스트를 만나면
> 실측 결과를 `current_status.md` 헤더에 적고 어느 유형인지 밝힌다.

아래 Slurm 규칙은 **`nexgem`을 통해 클러스터에 제출할 때만** 적용한다.

- **`nexgem`은 로그인 노드다.** GPU가 없고 `nvidia-smi`도 설치되어 있지 않다. 학습·추론·스윕·
  대규모 전처리는 Slurm `batch` 파티션에 `sbatch`로 제출한다. 로그인 노드에서는 편집·`git`·
  문서 작업과 가벼운 문법 검사만 한다.
- **노드 선택**: GPU가
  필요 없으면 `node1`~`node5`로 보내고, 필요하면 A5000(`gnode1-4`) → A6000(`gnode5`) →
  H100(`gnode6`) 순으로 **충분한 최저 등급**을 쓴다. 같은 등급에서는 한산한 노드를 고른다.
  Slurm에 GPU 타입이 등록돼 있지 않아 `--gres=gpu:<type>:N`은 동작하지 않는다 — `--nodelist`로 지정한다.
- **job 로그**는 `slurm_outputs/YYYY-MM-DD/HHMM/%x-%j.{out,err}`에 남긴다. 경로는 절대경로로 적고
  제출 전에 `mkdir -p`한다 (Slurm은 디렉토리를 만들지 않는다). 기존 승인에 포함된 제출은 재승인 없이 진행하고, 범위·예산 밖 제출은 사용자 승인을 받는다.
- **노드 종속 설정은 `scripts/node_env.sh` 하나로 모았다.** 인터프리터·경로는 이 스크립트가
  보고하는 값을 쓰고, 문서에 적힌 과거 값을 신뢰하지 않는다. `NGPU`는 Slurm 할당
  (`SLURM_GPUS_ON_NODE` → `CUDA_VISIBLE_DEVICES` → `nvidia-smi -L` 순)에서 유도된다.
- **Python**: `uv`로 관리하는 `ICF/.venv` (Python 3.12.11).
  재구축은 `uv venv --python 3.12 .venv && uv pip install -r requirements.txt`.
- **스레드 상한**: 다중 코어 노드에서 OpenMP 과다구독을 막기 위해 `OMP_NUM_THREADS=8`로 제한한다.
- **드라이버 호환성**: `.venv`의 torch 빌드가 요구하는 CUDA 런타임과 노드 드라이버가 맞아야 한다.
  cu130 빌드는 드라이버 **≥ 580**을 요구한다. 노드별 확인 현황은
  [`current_status.md`](current_status.md)에 있다. 새 노드를 처음 쓸 때는 점검 job으로
  `torch.cuda.is_available()`를 실측한다 — `device_count()`는 드라이버가 맞지 않아도 값을 반환한다.

## 6. 표준 검증 명령

> 4·6·7번은 GPU를 쓴다. **`nexgem`에서는 직접 실행하지 않고** `sbatch` 스크립트 안에서

```bash
# 7. SEAL 10-task hold-out (현재 유보 — PROJECT.md §3.1)
bash scripts/run_v120_seal_multi_gpu.sh <tag>
```

> ⚠️ **GPU 실행을 폴링으로 기다리지 말 것.**
> 진행 상황을 반복 확인하면 확인 1회당 도구 호출과 토큰이 소모된다(§218에서 5시간 사용량
> +7%p의 대부분이 여기서 발생했다). 대신 `scripts/run_and_wait.sh`를 **사용 가능한 도구의 백그라운드 실행 기능으로
> 단 한 번** 실행한다. 이 스크립트가 완주까지 블로킹한 뒤 완료 요약(과제별 fold-mean AUROC,

> 중간 확인이 꼭 필요하면 최소 10분 간격으로 제한한다.

```bash
# (참고) 6번의 실제 사용 예
bash scripts/run_and_wait.sh scripts/run_v121_shape_screen.sh v121_sh_v2 \
  "PYTHONPATH=$PWD $PYTHON scripts/analysis/branch_screen.py --tag v121_sh_v2 --candidate m_sh"
```
